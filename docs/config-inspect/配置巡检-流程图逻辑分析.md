# 配置巡检系统 - 流程图逻辑分析

> 分析日期：2026-07-24
> 来源：7张流程图 + 4张系统截图（策略列表/配置页、计划列表/详情页、结果查询/历史页） + 18张GaussDB表结构截图

---

## 一、整体架构概览

| 域 | 职责 | 关键表 |
|---|---|---|
| **策略管理** | 定义"查什么"（组件+检查项+治理规则） | 策略表/草稿表、组件表/草稿表、检查项表/草稿表 |
| **计划管理** | 定义"谁来查、什么时候查" | 巡检计划表、component_plan表 |
| **执行引擎** | 定时触发 + 结果同步 | 执行进度表、巡检明细表、巡检结果表 |
| **资源管理** | 机器/资源元数据 | 机器资源表、CMDB |

数据流向：**策略 → 计划 → 定时作业(automation) → vortex执行 → 结果回写**

---

## 二、ER 数据模型（图1）

### 核心关系链

```
策略(1) ──→ 组件(N) ──→ 检查项(N)
策略(1) ──→ 计划(N) ──→ 执行进度(N) ──→ 巡检明细(N)
```

### 关键设计决策

- **草稿表机制**：策略/组件/检查项各有草稿表，审批通过后才写入正式表、删除草稿
- **巡检结果表是聚合视图**：主键 = `策略ID + 部门ID + 组件ID + 检查项名 + 主机名 + 是否试运行`，**只存最新结果**
- **巡检明细表按作业粒度存**：同一计划执行两次 → 明细表两条记录（贺老师原话）
- **结果表数据来源**：执行进度表查单次作业ID → 调 automation 接口取结果 → 写入

### 表结构定义（GaussDB实际DDL，2026-07-24从数据库截图提取）

> 数据库：GaussDB (openGauss)，库名 `uopsaop`，模式 `onlaop`
> 存储引擎：USTORE（行存MVCC），表空间 pg_default
> 命名规范：`iop_mc_inspect_` 前缀，全字段 varchar，日期时间也用 varchar 存储

### 表关系总览（18张表）

```
策略域（6张）：
  strategy ←1:N→ component ←1:N→ item
  strategy_draft / component_draft / item_draft（审批草稿）

计划域（2张）：
  plan ←1:N→ component_plan（计划级入参）

执行域（4张）：
  execution（进度）→ exec_detail（明细，按次）
  execution → result（聚合，只存最新）
  execution → exec_miss（缺失记录）

资源域（1张）：
  resource（机器元数据，IP为主键）

治理域（3张）：
  govern（当前治理状态）
  govern_snapshot（每日快照）
  summary（运营统计）

例外域（2张）：
  exception（当前例外）
  exception_history（例外变更历史）
```

### ⚠️ 问题点（基于实际表结构）

1. **结果表主键无日期**：同天重复执行会覆盖——确认是设计意图（只存最新）
2. **exec_status 值域不一致**：执行进度表用 0/1/2，流程图中用 0/1/3——需统一（2=不需要再轮询 对应流程图的状态3）
3. **明细表 res2/res3 被挪用**：res2="是否例外"、res3="例外截止时间"——命名不规范，建议后续迁移为正式字段
4. **component_plan.param(10000) vs component.param_json(1000)**：计划级入参容量是策略级10倍，设计合理但需注意一致性
5. **plan表无 res1/res2**：被 batch_size/wait_time 占用，扩展性受限
6. **exception表无IP字段**：联合主键是 check_name+obj_name+host_name，但同一host_name可能有多个IP——需确认是否够用
7. **govern表无策略/计划关联**：只有 check_name+obj_name+host_name，无法追溯到具体哪个策略/计划产生的异常
8. **summary表 layer 字段**：01接入层/02业务层/03数据层/04系统层——这个分类维度在其他表中未出现，数据来源需确认

## 三、策略生命周期（图2）

### 新增巡检策略

```
点击"新增巡检策略" → 派发待办 → 处理待办
→ 填写策略信息（名称/标签/资源范围/巡检组件(多个)）
  - 资源从cmdb接口查询: http://10.225.169.132/rsmt/openapi/v1/resObject/uniteQuery
  - 巡检组件从akita接口查询: /akita-manage/rest/action/uip/getActionListForVortex

  - 调用automation操作执行接口（分别调用每个组件）
  - 接口返回作业id → 通过作业id查询执行明细（检查项/检查对象描述/标准值）
  - 注意：这里不用创建定时作业
→ 表格展示检查项（每条可填：跨中心/治理时效/治理组件/治理说明）
→ 点击"提交审批" → 数据入草稿表（策略/组件/检查项）
→ 管理人员审批（只读，不可更改）
  ├─ 通过：删草稿 → 写正式表 → 给各部门发"新增巡检计划"待办
  └─ 不通过：删草稿，结束
```

### 修改巡检策略

```
点击"修改巡检策略" → 派发待办 → 处理待办
→ 修改策略信息
→ 输入测试IP（默认加载当前表里该策略的测试IP，可修改）
→ 获取新检查项清单（同新增）
→ 左右对比展示（左新右旧），新表每条可填治理信息
→ 提交审批 → 入草稿表
→ 管理人员审批
  ├─ 通过：更新正式表 → 删草稿 → 禁用所有关联计划 → 发"确认巡检计划"待办
  └─ 不通过：删草稿，结束
```

### 删除巡检策略

```
点击"删除巡检策略" → 派发待办 → 处理待办
→ 查看相关信息 → 点击确认删除
→ 判断：是否有关联巡检计划？
  ├─ 是：提示"该策略已关联 XXX 巡检计划，请先联系创建人删除"，阻断
  └─ 否：提交审批
      ├─ 通过：删除正式表数据（策略/组件/检查项）
      └─ 不通过：无事发生
```

### ⚠️ 问题点

1. 修改策略后"禁用所有关联计划"影响面大——是否只禁用受影响组件的计划？
2. 删除策略未校验"是否有正在执行的作业"——vortex查不到策略数据会报错
3. 待办派发对象未明确（应为策略管理员/专业管理用户）

## 五、执行引擎（图4）- 核心后端逻辑

### 定时触发 → vortex接口（异步）

```
automation定时触发 → 调用vortex接口（必须异步）

vortex接口逻辑：
├─ 1. 判断试运行/正式运行（根据巡检计划id）
│   ├─ 试运行：
│   │   ├─ cur_trial_times >= trial_times → 返回空（不再执行）
│   │   └─ cur_trial_times < trial_times → 用trial_ips作为资源IP
│   └─ 正式运行：
│       策略id查资源范围 + 部门id → 调cmdb查IP序列
│
├─ 2. 遍历所有巡检组件（循环）
│   ├─ 对每个组件：调automation执行接口
│   │   路径: /automation/boltdog/openapi/v2/jobs/actions/execute
│   │   入参: _host=IP序列
│   │   返回: 作业id
│   └─ 对每个作业：存入执行进度表（状态=0）
│
└─ 3. 如果是试运行：cur_trial_times + 1
```

### 轮询任务（独立定时）

```
vortex工程里的定时接口：
→ 查执行进度表 status=0 的记录
→ 对每个作业id调automation查结果
  路径: /automation/boltdog/openapi/v2/job/logs/get
→ 有结果：
  - 状态置1
  - 写入巡检明细表
  - 写入巡检结果表
```

### 创建定时作业接口

```
路径: /automation/boltdog/openapi/v2/jobtimer/create
入参: crontab、操作id(vortex操作)、策略id、巡检计划id、部门id
返回: 定时作业id → 存入巡检计划表
```

### ⚠️ 问题点

1. vortex接口异步——执行失败怎么感知？依赖轮询兜底
2. 轮询无重试/超时——automation不可用时状态永远卡在0
3. 试运行次数用完后定时作业空转——应自动禁用或通知验收
4. 明细+结果写入无事务保证——可能不一致
5. 多个作业间无批次关联——部分成功部分失败无法整体回滚

  ├─ 代理端：和之前页面逻辑一致
  └─ 服务端：
      ├─ 资源范围蓝色提示"常态化运行范围由服务端巡检组件在内部指定"
      ├─ 隐藏"每批次机器数""批次间等待时间"
      └─ 试运行范围改为资源选择器（同策略服务端逻辑）
         注意：存入trial_ips的数据为JSON格式
→ 提交：
  - 入plan表
  - 有入参的组件写入component_plan表
```

### component_plan表存储规则

- **代理端**：同一策略里有些组件有入参有些没有 → 只存有入参的
- **服务端**：组件一定有入参 → 全都存
- **编辑/删除计划时同步修改/删除component_plan表**

## 九、执行时入参处理（图8）

```
根据execution表strategy_id → 策略表execType判断
（存量数据：execType=null 视为代理端执行）

├─ 代理端
│   遍历component表该策略的组件列表，根据paramJson判断是否有入参
│   ├─ 无入参：逻辑和之前一致（试运行和常态化都这样）
│   └─ 有入参：从component_plan表读取入参值 → 传给automation执行
│
└─ 服务端
    ├─ 试运行：
    │   从component_plan读入参 → 传automation
    │   结果以result出参形式输出
    │
    └─ 常态化运行：
        从component_plan读入参 → execObjectList置为"" → 传automation
        automation脚本自己调入库接口写结果
        ⚠️ execution表status置为3（表示由automation脚本自己入结果表）
        → 轮询任务需跳过status=3的记录
```

### 巡检计划状态

```

3(automation自行入库) ← 服务端常态化专用，轮询跳过

## 十一、全局问题汇总

| # | 问题 | 严重度 | 建议 |
|---|---|---|---|
| 1 | 轮询任务无重试/超时机制，作业可能永远卡在status=0 | 🔴 高 | 加最大重试次数(3次) + 超时(30min)自动置为失败 |
| 2 | 试运行次数用完后定时作业空转 | 🟡 中 | 达到次数后自动禁用定时作业 + 发待办通知验收 |
| 3 | 修改策略后"禁用所有关联计划"影响面过大 | 🟡 中 | 考虑只禁用受影响组件的计划，或改为"待确认"状态 |
| 4 | 删除策略未校验正在执行的作业 | 🔴 高 | 删除前检查执行进度表是否有status=0的记录 |
| 5 | 明细表+结果表写入无事务保证 | 🟡 中 | 用数据库事务包裹，或先写明细再写结果，失败可重试 |
| 6 | status=3的记录轮询任务需要跳过 | 🔴 高 | 轮询SQL加 WHERE status=0（需确认） |
| 7 | 入参配置策略级 vs 计划级优先级未定义 | 🟡 中 | 建议：计划级覆盖策略级，component_plan优先 |
| 8 | 服务端执行无法获取检查项清单 | 🟡 中 | 需和服务端脚本团队约定：execObjectList有值时输出检查项清单 |
| 9 | 编排类型暂不支持，但数据模型已预留 | 🟢 低 | MVP先不做，表结构兼容即可 |
| 10 | 结果表主键无日期，同天重复执行会覆盖 | 🟢 低 | 确认是设计意图（只存最新），文档标注清楚 |
